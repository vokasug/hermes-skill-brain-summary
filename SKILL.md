# brain-summary

Пересказ и архивация контента в базу знаний `~/gdrive/Brain/`. Для медиа это
оркестратор над двумя скиллами — строго в этом порядке: `media/yt-dlp` (скачать
аудио), затем `media/mlx-whisper` (распознать речь в текст). Два режима работы:
короткое саммари в Telegram (дефолт) и полная архивация в Brain.

## When to Use

- **«добавь в мозг» / «добавь в brain» / «+мозг» / «+brain»** (любое написание: мозг/brain/Brain) + ЧТО
  добавить — ПОЛНЫЙ режим (весь пайплайн, включая Brain и векторную базу):
  - ссылка на видео/аудио (YouTube или любой сайт yt-dlp) или медиа-файл → медиа-пайплайн;
  - ссылка на статью/страницу/пост, файл-документ, книга, готовый текст/сообщение →
    не-медиа пайплайн (трансформация в MD → sum-файл → Brain);
  - тема без ссылки («добавь в мозг про X») → поиск в интернете → лучший источник →
    не-медиа пайплайн.
  Тот же триггер ПОСЛЕ выданного саммари («добавь это в мозг», «+мозг» без ссылки) —
  довыполнение поверх уже полученного текста, без повторной обработки. Ответ в этом
  режиме — короткий, без повторной отправки резюме (см. «Ответ пользователю»).
- **«краткое содержание» / «саммари» / «перескажи» / «о чём ...»** + любое указание на
  контент (ссылка на медиа или статью/страницу, файл, готовый текст, тема) — режим
  САММАРИ: контент → текст → короткое резюме в Telegram, в Brain ничего не пишется.
- **Ссылка на YouTube без команды** (или с парой слов вокруг) — режим САММАРИ,
  медиа-пайплайн до ответа. Уточняющий вопрос ЗАПРЕЩЁН. Доп. вопросы в том же
  запросе — отвечать по транскрипту.
- **DON'T**: ссылка НЕ на YouTube без команды — скилл НЕ срабатывает (режим САММАРИ
  для не-медиа запускается только ЯВНЫМ «краткое содержание/саммари/перескажи»);
  «скачай видео» без пересказа (чистый yt-dlp); «распознай аудио, где ссылку уже дали
  раньше» (чистый mlx-whisper); живые стримы.

## Режимы

Режим определяется триггером (см. «Маршрутизация входа»):

- **Саммари** (дефолт для контента без команды «в мозг»): контент преобразуется
  в текст (медиа — шаги 1–6; не-медиа — шаг 1), и пользователю уходит только
  короткое резюме в Telegram (раздел «Ответ пользователю», вариант саммари).
  В Brain НИЧЕГО не сохраняется: шаги 7–8 медиа-пайплайна (копия транскрипта,
  sum-файл, синк векторной базы) и шаги 2–5 не-медиа пайплайна пропускаются.
  Локальные артефакты (mp3, MD-транскрипт в ~/result-mlx-whisper/) остаются на
  диске — они нужны для довыполнения и ответов на доп. вопросы.
- **Полный** («добавь в мозг/brain», «+мозг/+brain»): весь пайплайн, включая
  Brain и векторную базу.
- **Довыполнение** («добавь в мозг» / «+мозг» после выданного саммари того же
  контента): обработка контента НЕ повторяется — текст уже получен в этой сессии
  или лежит в ~/result-mlx-whisper/ (матч по ссылке/названию). Выполняются только
  недостающие этапы: для медиа — шаги 7, 8 и ответ (вариант довыполнения); для
  не-медиа — шаги 3, 4, 5 и ответ (вариант довыполнения). Повторное скачивание/транскрибация/извлечение
  контента ЗАПРЕЩЕНЫ. Резюме в ответе НЕ повторяется — оно уже отправлено в этой сессии.

## Правила формата ответа

### ЛИМИТЫ ОБЪЁМА

- **Ответ в Telegram** — цель: не более 3500 символов на всё сообщение целиком
  (шапка + резюме + пометки + блок метаданных). Это ориентир для генерации,
  а не гейт: длина не замеряется инструментально и не проверяется, лёгкое
  превышение допустимо. Почему 3500, а не телеграмовские 4096: мост Hermes
  перед отправкой конвертирует markdown в Telegram MarkdownV2 — точки, дефисы,
  скобки и другие спецсимволы получают экранирующий бэкслеш, и текст
  разрастается на 100–150+ символов; цель 3500 оставляет запас под это
  разрастание.
- **Подробный пересказ (`_sum.md`)** — ориентир: не более 16000 символов. Это
  предел для самых объёмных и насыщенных источников, а не цель: объём
  определяется полнотой материала, короткий или простой источник — короткий
  пересказ.
- **Понятность важнее краткости.** Лучше пункт из двух полных предложений,
  чем один телеграфный обрубок: каждый пункт резюме должен быть понятен без
  обращения к исходнику.

### ПУСТАЯ СТРОКА МЕЖДУ ПУНКТАМИ

**В разделе «# Ключевые тезисы» между любыми двумя соседними пунктами стоит
ровно одна пустая строка.** Пустая строка здесь — единственный разделитель:
по ней секция режется на записи при индексации в векторную базу и по ней текст
читается в Telegram, поэтому два пункта «вплотную» — нарушение формата, а не
стилистическая мелочь. Правило действует в каждом ответе без исключений;
перед отправкой текст ответа перечитывается и пункты «вплотную» исправляются.
Дефисы в начале пунктов не обязательны — писать их или нет, решает автор.

## Маршрутизация входа

Сначала РЕЖИМ, затем тип входа:

- Режим:
  - «добавь в мозг/brain», «+мозг/+brain» в запросе → ПОЛНЫЙ;
  - «добавь в мозг» / «+мозг» ПОСЛЕ выданного саммари (тот же контент в этой
    сессии) или для контента, чей транскрипт/MD уже есть в ~/result-mlx-whisper/
    (матч по ссылке или названию) → ДОВЫПОЛНЕНИЕ (см. «Режимы»);
  - всё остальное (голая YouTube-ссылка, «краткое содержание/саммари» + любой
    контент) → САММАРИ.
- Тип входа:
  - ссылка на медиа (YouTube или любой сайт yt-dlp) → медиа-пайплайн;
  - аудио/видео-ФАЙЛ → медиа-пайплайн, пропуская шаги 1–3: язык — по гейту
    языка (называемый источник или детект на 30 с), метаданные — по гейту
    шага 4 (запросить у пользователя с дефолтами);
  - статья/страница/книга/документ/готовый текст/тема без ссылки → не-медиа
    пайплайн.

## Procedure: медиа-пайплайн

0. **Загрузить оба скилла** (`skill_view media/yt-dlp`, `skill_view media/mlx-whisper`)
   и следовать их процедурам. Ниже — только склейка и гейты.

1. **Метаданные ДО скачивания** (это и шаг детекта языка, и источник контент-метаданных для шапки MD):
   ```bash
   ~/.local/bin/yt-dlp --js-runtimes node --skip-download \
     --print "%(title)s | %(uploader)s | %(upload_date)s | %(webpage_url)s | %(duration)s сек | %(view_count)s | %(description).500B" <URL>
   ```
   При 429/bot-check («Sign in to confirm you're not a bot») действовать по лестнице
   из скилла media/yt-dlp (шаг 3 Procedure), она общая для метаданных, субтитров и
   скачивания: сначала повтор как есть через 30–60 с (429 на субтитрах — IP rate-limit,
   решает тайминг повтора, а не браузер cookies), затем
   `--extractor-args "youtube:player_client=android,ios,tv"`, затем
   `--cookies-from-browser chrome`, затем оба вместе. Та же лестница действует для
   скачивания субтитров в шаге 3.
   По заголовку/описанию определить язык речи (гейт языка скилла mlx-whisper:
   источник языка должен быть называемым — «заголовок EN», либо детект на 30 с).
   Привычка/дефолт «ru» запрещены — видео бывает на любом языке.
   title/uploader/upload_date/webpage_url из этого вывода уходят в шаг 4 как
   `--meta-*` (ссылку брать из `webpage_url` — каноническую, без t=/si-параметров
   исходной ссылки юзера).

2. **Скачать аудио** (обычный путь, mp3 в result-yt-dlp):
   ```bash
   python3 ~/.hermes/skills/media/yt-dlp/scripts/download_dated.py --audio <URL>
   ```

3. **Субтитры — всегда пытаться скачать** (если у контента они есть в любом виде —
   ручные или auto): идут в коррекцию «вторым мнением» и заметно чинят ослышки
   (имена, термины). Язык — тот, что определён на шаге 1:
   ```bash
   ~/.local/bin/yt-dlp --js-runtimes node --skip-download --write-subs --write-auto-subs \
     --sub-langs "<lang>.*,<lang>" --sub-format "srt/vtt/best" \
     -o "/tmp/subs/%(title).100B.%(ext)s" --no-playlist <URL>
   ```
   Скачалось несколько вариантов (напр. `en-orig` и `en`) — брать ручные/оригинальные
   (`-orig`), а не auto. Ничего не скачалось — идём дальше без `--subs`, это не блокер.

4. **Транскрибировать** (длинные файлы — только `terminal(background=true, notify_on_complete=true)`
   + `process wait`; скилл mlx-whisper: VAD+STT+подготовка коррекции, ~5 мин на 40-мин аудио):
   Без `notify_on_complete=true` процесс завершится молча — придётся опрашивать `process wait`
   циклом (окно wait зажимается до 180 с, для 5-минутной транскрипции это несколько заходов).
   ```bash
   ~/.local/share/uv/tools/mlx-whisper/bin/python \
     ~/.hermes/skills/media/mlx-whisper/scripts/vad_transcribe.py "<mp3>" \
     --language <detected> \
     --terms "<имена/термины из заголовка и описания через запятую>" \
     --meta-title "<title из шага 1>" --meta-author "<uploader>" \
     --meta-date "<upload_date YYYYMMDD→YYYY-MM-DD>" --meta-url "<webpage_url>" \
     --subs "/tmp/subs/<файл субтитров>.srt"   # только если шаг 3 дал файл
   ```
   `--meta-*` — контент-метаданные для шапки MD (блок пишется всегда, первым, перед
   техническими строками). Для не-YouTube контента заполнять по аналогии из того, что
   известно о источнике: название, автор, дата публикации, ссылка (каноническая, без
   t=/si-параметров). **ГЕЙТ**: если метаданные частично или полностью определить нельзя
   (передан готовый файл или источник их не содержит) — обязательно ЗАПРОСИТЬ недостающие
   у пользователя, предложив вариант по умолчанию для отсутствующих значений: название —
   имя файла с расширением; автор — unknown (если источник — запись или конспект Plaud, маркеры «note 1/1», «auto_sum_note», «consumer_note», «Meeting Minutes», — то «plaud»); дата публикации — предложить текущую дату;
   ссылка — переданная пользователем или найденная ссылка интернет, для файла — полный
   относительный путь к файлу. Передавать пустые значения (гейт в vad_transcribe.py падает
   на пустом `--meta-*`) или не спрашивать пользователя ЗАПРЕЩЕНО.
   `--subs` передаёт субтитры в этап коррекции как «второе мнение» поверх транскрипта Whisper
   (расхождения решаются знаниями, числа всегда остаются от Whisper — числовой гейт
   в коде; подробности архитектуры — в скилле mlx-whisper). Использование субтитров
   фиксируется в шапке MD.
   `--terms` — имена/термины из заголовка и описания через запятую: этап коррекции
   исправляет их написание в транскрипте (без `--terms` скрипт тоже работает).

5. **Коррекция — обязательна, когда скрипт напечатал строку `PAYLOAD <путь>`**
   (нет строки — коррекция не требовалась, MD уже финальный). Советчик — основная
   модель (ты), судья — гейты скрипта:
   1. Прочитать payload-JSON; правила коррекции — в его поле `instructions`
      (править только ослышки и написание терминов, поток слов/пунктуацию/числа не трогать,
      вывести полный текст целиком без комментариев). Правки терминов охватывают ВСЕ
      регистровые варианты написания (omlx/OMLX/Omelix — одно правило на термин,
      регистронезависимый матч с заменой на каноническую форму), а не только формы
      из списка канонов. `base_text` длинный — одна строка
      100+ тыс. символов: `read_file` обрезает на ~100 тыс. и режет по границе строки, поэтому
      читать срезами через `execute_code` (`print(bt[0:20000])` и т.д.) кусками ~20 тыс.
      символов (кап stdout — 50 КБ, кириллица 2 байта/символ), а не мелкими кусками.
   2. Записать исправленный `base_text` ЦЕЛИКОМ (весь транскрипт одним проходом, без
      деления на куски) в файл `<имя>.corrected.txt` рядом с payload.
   3. Применить с гейтами:
      ```bash
      ~/.local/share/uv/tools/mlx-whisper/bin/python \
        ~/.hermes/skills/media/mlx-whisper/scripts/vad_transcribe.py \
        --apply-corrections "<имя>.correct-payload.json" "<имя>.corrected.txt"
      ```
      exit 0 — MD переписан с правками (список — в `<имя>.corrections.md`); exit 1 —
      вывод отклонён word-diff/числовым гейтом, MD остался на regex-базе: разобрать
      сообщение REJECTED и переписать corrected.txt точнее (не силой проталкивать правки,
      а сократить до реальных ослышков).

6. **Прочитать MD-результат целиком** (`read_file`) из `~/result-mlx-whisper/`.
   В режиме САММАРИ дальше — сразу раздел «Ответ пользователю» (вариант саммари).

7. **Копия транскрипта в Brain** — ТОЛЬКО полный режим / довыполнение
   (`~/gdrive/Brain/`): прочитать ПОЛНОСТЬЮ
   `~/gdrive/Brain/AGENTS.md` и по его правилам выбрать предметную папку
   (Education/Family/Finances/Health/Hobbies/Private/Work — границы между папками
   описаны в разделах «Чего здесь быть не должно»). Скопировать MD транскрипта в неё
   с тем же именем файла (`YYYY-MM-DD_<имя>.md`) и убедиться чтением копии, что она
   на месте. Если `~/gdrive/Brain/` недоступна — ответ не блокировать, но прямо
   сообщить об этом в блоке метаданных (раздел «Ответ пользователю»).

8. **Подробный пересказ (sum-файл) + синк векторной базы** — ТОЛЬКО полный режим /
   довыполнение — в ту же папку Brain, что и копия
   транскрипта: файл `YYYY-MM-DD_<имя>_sum.md` (`_sum` добавляется ПОСЛЕ имени,
   перед расширением). Начало файла — блок контент-метаданных, идентичный шапке полного MD
   транскрипта (строки Название/Автор/Дата публикации/Ссылка — те же значения),
   далее пустая строка и пересказ по ТОЙ ЖЕ структуре и правилам, что ответ в
   Telegram («# Главная мысль» / «# Ключевые тезисы» / «# Вывод», язык, стиль,
   содержание — см. «Ответ пользователю»), но ПОДРОБНЫЙ: больший запас объёма позволяет
   дать больше ключевых тезисов и подробнее изложить Главную мысль, тезисы и
   Вывод — глубже раскрыть аргументы, детали, примеры и оговорки автора. Ориентир
   объёма — не более 16000 символов (см. «Правила формата ответа»).
   После записи sum-файла ВСЕГДА запускать синк векторной базы скилла
   `brain-vector`, не дожидаясь крона (крон каждые 4 ч остаётся страховкой):
   `~/.local/share/uv/tools/mlx-embeddings/bin/python
   ~/.hermes/profiles/personal/skills/brain-vector/scripts/brain_index.py`. Итог синка обрабатывать так:
   - синк прошёл без строк «!! не распарсился» — ничего дополнительно не писать,
     в ответе синк не упоминать;
   - есть строка «!! не распарсился: <файл>» — исправить sum-файл (частая причина:
     перед блоком метаданных стоит заголовок — файл должен начинаться сразу со
     строки `- **Название:**`) и перезапустить синк до чистого прохода; в ответе,
     в блоке «# Метаданные и размещение», последней строкой (после «Папка Brain»)
     добавить: «Векторная база: была ошибка парсинга sum-файла, исправлено, синк
     выполнен»;
   - синк не удался (скрипт упал, окружение недоступно) — ответ НЕ блокировать;
     в блоке «# Метаданные и размещение», последней строкой (после «Папка Brain»)
     добавить: «Векторная база: синк не выполнен (<причина>), файл подхватит крон».

## Procedure: не-медиа пайплайн (статьи, книги, файлы, текст, темы)

Режим определён в «Маршрутизации входа»: САММАРИ — только шаг 1, затем раздел
«Ответ пользователю» (вариант саммари); ПОЛНЫЙ — шаги 1–5 целиком; довыполнение —
шаги 3, 4, 5 (шаг 1 не повторяется, контент уже получен).

1. **Получить контент**:
   - ссылка на статью/страницу/пост — tavily extract (basic; если пусто или защита —
     advanced, затем blocked-page-recovery);
   - тема без ссылки («добавь в мозг про X») — tavily search, выбрать лучший
     первичный источник, затем extract его;
   - файл-документ — прочитать (`read_file` сам извлекает docx/pdf/pptx и т.п.);
     .html — конвертер `scripts/html2md.py` этого скилла:
     `python3 ~/.hermes/skills/brain-summary/scripts/html2md.py <файл.html>`;
   - готовый текст/пересланное сообщение — как есть.

2. **Метаданные** (только ПОЛНЫЙ режим; в САММАРИ шаг пропускается — метаданные
   для шапки ответа берутся из источника как есть, неопределившееся — «неизвестен»,
   опрос пользователя не требуется) — тот же гейт, что в шаге 4 медиа-пайплайна:
   название (заголовок страницы/документа), автор, дата публикации, ссылка.
   Часть не определяется — обязательно запросить у пользователя с дефолтами:
   название — заголовок или имя файла с расширением; автор — unknown (если
   источник — запись или конспект Plaud, маркеры «note 1/1», «auto_sum_note»,
   «consumer_note», «Meeting Minutes», — то «plaud»); дата — предложить текущую;
   ссылка — переданная или найденная, для файла — полный относительный путь к
   файлу. Пустые значения и молчаливый пропуск запрещены.

3. **MD-файл** (только ПОЛНЫЙ режим / довыполнение): первым — блок
   контент-метаданных (`- **Название:**`,
   `- **Автор:**`, `- **Дата публикации:**`, `- **Ссылка:**`), пустая строка, далее
   контент ЦЕЛИКОМ в markdown (заголовки, таблицы, списки сохранить/преобразовать).
   Это трансформация формата, а НЕ пересказ: содержание не сжимать. Имя файла:
   `YYYY-MM-DD_<короткое название>.md`.

4. **Sum-файл — в полном режиме создаётся ВСЕГДА** (в саммари не создаётся),
   по тем же правилам, что шаг 8 медиа-пайплайна: файл
   `YYYY-MM-DD_<короткое название>_sum.md` (суффикс `_sum`
   после имени, перед расширением) в той же папке Brain, что и полный MD.
   Начало — блок контент-метаданных, идентичный шапке полного MD (те же значения
   Название/Автор/Дата публикации/Ссылка), далее пустая строка и подробный
   пересказ по структуре и правилам раздела «Ответ пользователю» («# Главная
   мысль» / «# Ключевые тезисы» / «# Вывод», пустая строка между тезисами).
   Ориентир объёма — не более 16000 символов, предел для самых насыщенных
   источников, а не цель (см. «Правила формата ответа»). Без `_sum.md` материал не
   попадёт в векторную базу brain-vector (индексируются только `*_sum.md`) —
   пропуск sum-файла запрещён. Синк векторной базы — как в шаге 8 медиа-пайплайна.

5. **В Brain + ответ** (только ПОЛНЫЙ режим / довыполнение): как шаг 7
   медиа-пайплайна — прочитать `~/gdrive/Brain/AGENTS.md` ПОЛНОСТЬЮ, выбрать
   папку по его правилам (границы в разделах «Чего здесь быть не должно»),
   записать файл, убедиться чтением копии. Ответ — по разделу «Ответ
   пользователю»; от медиа-варианта он отличается только отсутствием пометок о
   распознавании.

## Ответ пользователю (оба пайплайна)

Ответ — на языке запроса юзера.

- **Первая строка ответа** — одной строкой: название видео, автор/канал,
  длительность, язык. Ответ начинается СРАЗУ с этой строки: служебные преамбулы
  («файлы проверены», «транскрипт готов» и т. п.) ЗАПРЕЩЕНЫ —
  результаты проверок и размещения файлов в тексте ответа не упоминаются вовсе.
  Ссылка в начале ответа ЗАПРЕЩЕНА: Telegram строит по
  первой ссылке сообщения embed-превью сайта, которое раздувает сообщение;
  ссылка присутствует ровно один раз — в блоке метаданных в конце.

**Цель резюме**: передать основные идеи, существенные факты, аргументы и выводы
автора без искажения смысла.

**Структура (строго, заголовки как указано):**
```
# Главная мысль
1–2 предложения.

# Ключевые тезисы
Пункты; дефисы в начале не обязательны. Один пункт — одна законченная мысль.
Между ЛЮБЫМИ двумя соседними пунктами — ровно одна ПУСТАЯ СТРОКА
(см. «Правила формата ответа»).
Количество пунктов определяется содержимым материала: столько, сколько
нужно, чтобы покрыть все существенные идеи и выводы без второстепенных
деталей; жёсткого ограничения нет. Ориентир объёма всего ответа — не более
3500 символов; понятность пунктов важнее краткости.

# Вывод
1–3 предложения: основной итог или практическое значение текста.
```
Объём всего ответа (шапка + резюме + пометки + блок метаданных) — ориентир
не более 3500 символов, см. «Правила формата ответа».

**Блок метаданных — последний раздел ответа** (после резюме, ответов на доп.
вопросы и пометок; отдельным сообщением Telegram его отправить невозможно —
из одного ответа агента уходит одно сообщение). Формат — помеченные строки
без пунктов, списков и буллетов:
```
# Метаданные и размещение
Название: <title>
Автор: <uploader>
Дата публикации: <YYYY-MM-DD или «неизвестна»>
Ссылка: `<webpage_url>`
Папка Brain: <Education|Family|Finances|Health|Hobbies|Private|Work>
```
Ссылка — строго в `code`-формате (некликабельная, копируется тапом): любая
кликабельная ссылка в сообщении даёт embed-превью сайта. Папка Brain — только
название папки, без имён файлов. Остальные значения — те же, что в шапке MD
транскрипта. Если `~/gdrive/Brain/` была недоступна (шаг 7), строка
«Папка Brain» заменяется на: «Brain недоступна — файлы остались в
~/result-mlx-whisper/». Если на шаге 8 был сбой синка векторной базы
(ошибка парсинга sum-файла, даже исправленная, или падение самого синка) —
последней строкой блока, после «Папка Brain», добавить строку «Векторная
база: ...» с формулировкой из шага 8; при чистом синке эта строка не
добавляется.

**Вариант САММАРИ (без Brain):** строки «Папка Brain» и «Векторная база» в
блоке метаданных отсутствуют. Последней строкой всего ответа, после блока
метаданных, — ровно одна короткая строка-вопрос: «Добавить в мозг?». Ответ
пользователя «да» / «добавь» / «+мозг» — это довыполнение, см. «Маршрутизация
входа».

**Вариант ДОВЫПОЛНЕНИЕ (после выданного в этой сессии саммари):** резюме
(«# Главная мысль» / «# Ключевые тезисы» / «# Вывод») НЕ отправляется
повторно — пользователь его уже получил, дубль превращается в шум. Ответ
короткий: первая строка (название, автор/канал, длительность, язык), одна-две
строки подтверждения, что файлы размещены (без служебных подробностей),
затем блок «# Метаданные и размещение» со строкой «Папка Brain» (и строкой
«Векторная база», если был сбой синка). Строка-вопрос «Добавить в мозг?»
не добавляется — материал уже в Brain.

**Язык:**
- Грамотный литературный русский, нейтральный информационно-деловой стиль.
- Не переводить с английского слово в слово — это касается не только идиом
  и терминов, но и любых слов без прямого русского эквивалента (subtle,
  thorough, nuanced и т. п.). Устоявшиеся эквиваленты — использовать
  (stepping stone → «промежуточный этап», а не «ступенчатый камень»).
  Запрещено подбирать русское слово «по оттенку смысла» и вставлять его в
  сочетание, где оно не употребляется: «subtle design taste» → «тоньше
  в дизайне» — ошибка. Если устоявшегося эквивалента нет, не сжимать нюанс
  в одно слово, а раскрыть его фразой о том, что конкретно происходит:
  «subtle design taste» → «точнее работает с мелкими деталями, анимациями
  и компоновкой»; «more thorough» → «тщательнее проверяет код». Критерий:
  русская фраза называет наблюдаемое действие или свойство, а не оттенок.
- Без разговорной лексики, сленга, жаргона, эмоциональных оценок, риторических
  вопросов и фамильярных обращений.
- Писать так, как пишет человек-редактор в хорошей профессиональной и
  художественной литературе: глагол вместо отглагольного существительного,
  простая синтаксическая конструкция, только те сочетания слов, которые
  реально встречаются в печатных текстах. Критерий для каждого предложения:
  могло бы оно стоять в книге или статье, написанной человеком, или это
  калька, которую породила модель.
- Каждое словосочетание должно быть общепринятым в русском языке. Проверять
  управление ключевых слов: существительное требует свойственных ему
  предлога и падежа («по цене $500», «курс 90 рублей за доллар» — но не
  «при курсе $500»). Если конструкция не встречается в живых текстах,
  переписать её простой формулировкой, близкой к словам источника, вместо
  того чтобы изобретать новое сочетание.
- Предложения логичные, законченные, грамматически корректные; предпочтительны
  короткие и средние; длинные сложные разбивать, если это улучшает читаемость.

**Содержание:**
- Сохранять ключевые факты, даты, цифры, имена, причинно-следственные связи и
  оговорки автора.
- Не добавлять собственных интерпретаций, предположений и сведений, которых нет
  в источнике.
- Исключать повторы, второстепенные детали и иллюстративные примеры, если они не
  важны для понимания вывода.
- Противоречия и неопределённости в тексте — кратко отражать, а не устранять
  от себя.
- Таймкоды в резюме запрещены — они нужны только внутри для навигации по
  транскрипту.

**Внутренняя проверка перед отправкой:** (1) нет фактических искажений; (2) все
предложения грамматически корректны; (3) нет разговорной лексики, повторов и
«воды»; (4) структура соблюдена, включая пустую строку между каждыми
соседними пунктами «Ключевых тезисов» (см. «Правила формата ответа»); (5) объём
держится в ориентире ~3500 символов, а каждый пункт понятен без обращения
к исходнику.

- **Ответы на дополнительные вопросы из запроса** — отдельным блоком ПОСЛЕ
  резюме (структуру резюме они не нарушают), цитируя конкретные места
  транскрипта (по таймстампу — тут таймкоды уместны), а не пересказ.
- Пометка о ненадёжном распознавании (только медиа-пайплайн) — только когда
  «каша», сомнительные имена или термины реально касаются фактов, цифр или
  имён, вошедших в резюме: тогда после резюме отдельной строкой указать, какие
  именно пункты это затрагивает. Если ненадёжные фрагменты — только обрывки
  реакций поверх шума, а все факты, числа и имена резюме подтверждены
  субтитрами или списком терминов, пометку не добавлять вовсе: она
  превращается в формальный шум.

## Pitfalls

- **Путь к файлу с `$` в имени — только одинарные кавычки**: в двойных кавычках shell
  раскрывает `$200` из названия видео ("($200 Plans...") как переменную `$2`, скрипт
  получает битый путь и печатает `SKIP (not found)`. Все пути и `--meta-*` значения
  с `$` передавать в 'одинарных' кавычках.
- **Язык — гейт**: язык брать только из называемого источника — заголовок/описание
  (`yt-dlp --print` до скачивания) либо детект на первых 30 с. Запуск по привычке
  или дефолту («обычно всё русское») даёт транскрипт-кашу и полный перезапуск.
- **Триггер сужен намеренно**: ссылка не на YouTube без команды скилл НЕ запускает —
  не-медиа контент идёт только по явной команде («добавь в мозг/brain» — полный
  режим; «краткое содержание/саммари/перескажи» — саммари без Brain).
  Не «улучшать» это обратно: авто-срабатывание на любую ссылку давало ложные запуски.
- **Режим саммари ничего не пишет в Brain**: ни копии транскрипта, ни sum-файла,
  ни синка векторной базы — только ответ в Telegram. Артефакты в ~/result-yt-dlp/
  и ~/result-mlx-whisper/ остаются: по последующему «добавь в мозг» выполняется
  довыполнение (медиа — шаги 7/8 + ответ, не-медиа — шаги 3/4/5 + ответ) поверх
  них; повторная транскрибация/скачивание запрещены.
- Метаданные считать до скачивания: они же дают title для `--terms`.
- **Формат резюме**: строгая структура «# Главная мысль / # Ключевые
  тезисы / # Вывод» (см. «Ответ пользователю»), нейтральный информационно-деловой
  стиль, без разговорной лексики и «воды» — разговорный «пересказ другу» не
  соответствует формату. Таймкоды в резюме запрещены — остаются только в ответах
  на доп. вопросы (цитаты из транскрипта).
- **Пустая строка между пунктами**: требование формата, а не стилистика —
  два пункта «вплотную» портят ответ даже при безупречном содержании;
  перед отправкой текст перечитывается целиком.
- Оба артефакта (mp3 + MD) остаются в `~/result-yt-dlp/` и `~/result-mlx-whisper/`
  в обоих режимах; копии MD и sum-файла — в `~/gdrive/Brain/<предметная папка>/`
  только в полном режиме (шаги 7/8) — когда юзер потом задаёт доп. вопросы
  по видео, отвечать по сохранённому транскрипту без повторной транскрипции.
- **Доп. вопросы после пересказа — только по готовому транскрипту**: полный MD
  уже содержит всё содержание видео, поэтому для ответов
  на последующие вопросы НЕ ходить в интернет (tavily/web_search) и НЕ вызывать
  снова yt-dlp (метаданные, описание, субтитры) — сначала перечитать
  `~/result-mlx-whisper/YYYY-MM-DD_<имя>.md` (путь виден в заголовке MD, источник
  mp3 — в метаданных) и цитировать ответ с таймстампами оттуда. Внешние
  инструменты — только если в транскрипте реально нет нужных данных (например,
  юзер спрашивает про то, чего в речи не было: описание под роликом, ссылки,
  комментарии).
