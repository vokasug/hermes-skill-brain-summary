## ПРАВИЛО №1 — ЛИМИТ 3800 СИМВОЛОВ, ПРОВЕРЯЕТСЯ ВСЕГДА И ПЕРВЫМ

**Ни один ответ этого скилла не отправляется без инструментального замера длины.**

1. Готовый текст ответа целиком (шапка + резюме + пометки + блок
   метаданных — ВСЁ вместе) измеряется реальным вызовом инструмента
   (`execute_code`/`terminal`, `len()`).
   Подсчёт «в уме», «на глаз», «по ощущению» ЗАПРЕЩЁН и приравнивается к
   отсутствию подсчёта.
2. Замер ≤ 3800 символов — ответ можно отправлять.
3. Замер > 3800 — отправка ЗАПРЕЩЕНА: переписать компактнее и замерить снова,
   повторять до прохождения. Сокращение — только за счёт формулировок: ни один
   тезис, факт, число, имя или пометка не снимаются ради лимита.
4. Отправка без замера или с перебором лимита — грубое нарушение скилла, даже
   если содержание безупречно.
5. Почему 3800, а не телеграмовские 4096: мост Hermes перед отправкой
   конвертирует markdown в Telegram MarkdownV2 — каждая точка, дефис, скобка и
   прочие спецсимволы получают экранирующий бэкслеш, и текст разрастается на
   100–150+ символов (насыщенный цифрами текст — сильнее). Лимит 4096
   применяется к разросшемуся тексту, и ответ 3990–4000 символов уходит
   двумя сообщениями. 3800 — рабочий запас под экранирование.

Остальные разделы скилла не отменяют и не ослабляют это правило.

## ПРАВИЛО №2 — ПУСТАЯ СТРОКА МЕЖДУ ПУНКТАМИ, ПРОВЕРЯЕТСЯ ВМЕСТЕ С ЛИМИТОМ

**В разделе «# Ключевые тезисы» между любыми двумя соседними пунктами стоит
ровно одна пустая строка.** Два буллета подряд без пустой строки между ними —
нарушение формата ответа, а не стилистическая мелочь.

1. Проверка — тем же вызовом `execute_code`/`terminal`, что и замер длины
   (ПРАВИЛО №1): перед отправкой программно убедиться, что в готовом тексте
   нет двух строк, начинающихся с `- `, идущих подряд без пустой строки между
   ними. Подсчёт «на глаз» запрещён так же, как и для лимита 3800.
2. Нарушение найдено — вставить пустые строки и повторить замер длины
   (текст станет длиннее). Оба замера — символы и структура — делаются
   до отправки, в каждом ответе.

## When to Use

- **«добавь в мозг» / «добавь в brain»** (любое написание: мозг/brain/Brain) + ЧТО
  добавить — главный триггер; дальше маршрутизация по типу входа (шаг 0 Procedure):
  - ссылка на видео/аудио (YouTube или любой сайт yt-dlp) или медиа-файл → медиа-пайплайн;
  - ссылка на статью/страницу/пост, файл-документ, книга, готовый текст/сообщение →
    не-медиа ветка (трансформация в MD → Brain);
  - тема без ссылки («добавь в мозг про X») → поиск в интернете → лучший источник →
    не-медиа ветка.
- **Ссылка на YouTube без команды** (или с парой слов вокруг) — медиа-пайплайн:
  скачать → транскрибировать → пересказать. Уточняющий вопрос ЗАПРЕЩЁН.
- «о чём видео/ролик», «краткое содержание» + YouTube-ссылка — то же; доп. вопросы в
  том же запросе — отвечать по транскрипту.
- **DON'T**: ссылка НЕ на YouTube без «добавь в мозг/brain» — скилл НЕ срабатывает;
  любые другие команды/вопросы со ссылкой — НЕ срабатывает (кроме YouTube-ссылки);
  «скачай видео» без пересказа (чистый yt-dlp); «распознай аудио, где ссылку уже дали
  раньше» (чистый mlx-whisper); живые стримы.

# Video Summary («о чём видео» + «добавь в мозг»)

Триггеры медиа-пайплайна: (а) ссылка на YouTube БЕЗ команды — или с парой слов
вокруг; (б) «о чём видео / о чём ролик / краткое содержание» + YouTube-ссылка;
(в) «добавь в мозг/brain» + ссылка на медиа (YouTube или любой сайт yt-dlp) либо
аудио/видео-файл. Ссылка НЕ на YouTube без команды скилл не запускает — не-медиа и прочие
источники идут только через явное «добавь в мозг/brain». Действие медиа-пайплайна
одно: скачать → транскрибировать → пересказать → в Brain, без уточняющих вопросов.
Плюс: если в том же запросе есть дополнительные вопросы к видео — ответить и на них.

Это оркестратор над двумя скиллами — строго в этом порядке:

1. `media/yt-dlp` — скачать аудио
2. `media/mlx-whisper` — распознать речь в текст

## Procedure

0. **Маршрутизация входа** (по триггеру, см. When to Use):
   - YouTube-ссылка без команды или «о чём видео» + YouTube → медиа-пайплайн, шаги 1–6;
   - «добавь в мозг/brain» + ссылка на медиа (любой сайт yt-dlp) → шаги 1–6;
   - «добавь в мозг/brain» + аудио/видео-ФАЙЛ → шаги 1–6, пропуская 2–3b: язык —
     по гейту шага 4 скилла mlx-whisper (назвать источник или детект на 30 с),
     метаданные — по гейту шага 4 (запросить у пользователя с дефолтами);
   - «добавь в мозг/brain» + статья/страница/книга/документ/готовый текст/тема без
     ссылки → не-медиа ветка, шаги A–D (после шага 6).

1. **Загрузить оба скилла** (`skill_view media/yt-dlp`, `skill_view media/mlx-whisper`) и следовать их процедурам. Ниже — только склейка и гейты.

2. **Метаданные ДО скачивания** (это и шаг детекта языка, и источник контент-метаданных для шапки MD):
   ```bash
   ~/.local/bin/yt-dlp --js-runtimes node --skip-download \
     --print "%(title)s | %(uploader)s | %(upload_date)s | %(webpage_url)s | %(duration)s сек | %(view_count)s | %(description).500B" <URL>
   ```
   При 429/bot-check («Sign in to confirm you're not a bot») повторить с
   `--cookies-from-browser safari` — YouTube периодически режет вызовы без cookies,
   с cookies проходит (та же лестница уже встроена в download_dated.py шага 3;
   то же правило действует для скачивания субтитров в шаге 3b).
   По заголовку/описанию определить язык речи (гейт шага 4 скилла mlx-whisper:
   источник языка должен быть называемым — «заголовок EN», либо детект на 30 с).
   Привычка/дефолт «ru» запрещены — видео бывает на любом языке.
   title/uploader/upload_date/webpage_url из этого вывода уходят в шаг 4 как
   `--meta-*` (ссылку брать из `webpage_url` — каноническую, без t=/si-параметров
   исходной ссылки юзера).

3. **Скачать аудио** (обычный путь, mp3 в result-yt-dlp):
   ```bash
   python3 ~/.hermes/skills/media/yt-dlp/scripts/download_dated.py --audio <URL>
   ```

3b. **Субтитры — всегда пытаться скачать** (если у контента они есть в любом виде —
   ручные или auto): идут в коррекцию «вторым мнением» и заметно чинят ослышки
   (имена, термины). Язык — тот, что определён на шаге 2:
   ```bash
   ~/.local/bin/yt-dlp --js-runtimes node --skip-download --write-subs --write-auto-subs \
     --sub-langs "<lang>.*,<lang>" --sub-format "srt/vtt/best" \
     -o "/tmp/subs/%(title).100B.%(ext)s" --no-playlist <URL>
   ```
   Скачалось несколько вариантов (напр. `en-orig` и `en`) — брать ручные/оригинальные
   (`-orig`), а не auto. Ничего не скачалось — идём дальше без `--subs`, это не блокер.

4. **Транскрибировать** (длинные файлы — только `terminal(background=true, notify_on_complete=true)`
   + `process wait`; скилл mlx-whisper: VAD+STT+подготовка коррекции, ~5 мин на 40-мин аудио):
   Без `notify_on_complete=true` процесс завершится молча — придётся опрашивать `process wait`
   циклом (окно wait зажимается до 180 с, для 5-минутной транскрипции это несколько заходов).
   ```bash
   ~/.local/share/uv/tools/mlx-whisper/bin/python \
     ~/.hermes/skills/media/mlx-whisper/scripts/vad_transcribe.py "<mp3>" \
     --language <detected> \
     --terms "<имена/термины из заголовка и описания через запятую>" \
     --meta-title "<title из шага 2>" --meta-author "<uploader>" \
     --meta-date "<upload_date YYYYMMDD→YYYY-MM-DD>" --meta-url "<webpage_url>" \
     --subs "/tmp/subs/<файл субтитров>.srt"   # только если шаг 3b дал файл
   ```
   `--meta-*` — контент-метаданные для шапки MD (блок пишется всегда, первым, перед
   техническими строками). Для не-YouTube контента заполнять по аналогии из того, что
   известно о источнике: название, автор, дата публикации, ссылка (каноническая, без
   t=/si-параметров). **ГЕЙТ**: если метаданные частично или полностью определить нельзя
   (передан готовый файл или источник их не содержит) — обязательно ЗАПРОСИТЬ недостающие
   у пользователя, предложив вариант по умолчанию для отсутствующих значений: название —
   имя файла с расширением; автор — unknown (если источник — запись или конспект Plaud, маркеры «note 1/1», «auto_sum_note», «consumer_note», «Meeting Minutes», — то «plaud»); дата публикации — предложить текущую дату;
   ссылка — переданная пользователем или найденная ссылка интернет, для файла — полный
   относительный путь к файлу. Передавать пустые значения (гейт в vad_transcribe.py падает
   на пустом `--meta-*`) или не спрашивать пользователя ЗАПРЕЩЕНО.
   `--subs` передаёт субтитры в этап коррекции как «второе мнение» поверх транскрипта Whisper
   (расхождения решаются знаниями, числа всегда остаются от Whisper — числовой гейт
   в коде; подробности архитектуры — в скилле mlx-whisper). Использование субтитров
   фиксируется в шапке MD.
   `--terms` — имена/термины из заголовка и описания через запятую: этап коррекции
   исправляет их написание в транскрипте (без `--terms` скрипт тоже работает).

4b. **Коррекция — обязательна, когда скрипт напечатал строку `PAYLOAD <путь>`**
   (нет строки — коррекция не требовалась, MD уже финальный). Советчик — основная
   модель (ты), судья — гейты скрипта:
   1. Прочитать payload-JSON; правила коррекции — в его поле `instructions`
      (править только ослышки и написание терминов, поток слов/пунктуацию/числа не трогать,
      вывести полный текст целиком без комментариев).
   2. Записать исправленный `base_text` ЦЕЛИКОМ (весь транскрипт одним проходом, без
      деления на куски) в файл `<имя>.corrected.txt` рядом с payload.
   3. Применить с гейтами:
      ```bash
      ~/.local/share/uv/tools/mlx-whisper/bin/python \
        ~/.hermes/skills/media/mlx-whisper/scripts/vad_transcribe.py \
        --apply-corrections "<имя>.correct-payload.json" "<имя>.corrected.txt"
      ```
      exit 0 — MD переписан с правками (список — в `<имя>.corrections.md`); exit 1 —
      вывод отклонён word-diff/числовым гейтом, MD остался на regex-базе: разобрать
      сообщение REJECTED и переписать corrected.txt точнее (не силой проталкивать правки,
      а сократить до реальных ослышков).

5. **Прочитать MD-результат целиком** (`read_file`) из `~/result-mlx-whisper/`.

5b. **Копия транскрипта в Brain** (`~/gdrive/Brain/`): прочитать ПОЛНОСТЬЮ
   `~/gdrive/Brain/AGENTS.md` и по его правилам выбрать предметную папку
   (Education/Family/Finances/Health/Hobbies/Private/Work — границы между папками
   описаны в разделах «Чего здесь быть не должно»). Скопировать MD транскрипта в неё
   с тем же именем файла (`YYYY-MM-DD_<имя>.md`) и убедиться чтением копии, что она
   на месте. Если `~/gdrive/Brain/` недоступна — ответ не блокировать, но прямо
   сообщить об этом в блоке метаданных (шаг 6).

5c. **Подробный пересказ (sum-файл)** — в ту же папку Brain, что и копия
   транскрипта: файл `YYYY-MM-DD_<имя>_sum.md` (`_sum` добавляется ПОСЛЕ имени,
   перед расширением). Начало файла — блок контент-метаданных, идентичный шапке полного MD
   транскрипта (строки Название/Автор/Дата публикации/Ссылка — те же значения),
   далее пустая строка и пересказ по ТОЙ ЖЕ структуре и правилам, что ответ в
   Telegram («# Главная мысль» / «# Ключевые тезисы» / «# Вывод», язык, стиль,
   содержание — см. шаг 6), но ПОДРОБНЫЙ: больший запас лимита позволяет больше
   ключевых тезисов и подробнее изложить Главную мысль, тезисы и Вывод — глубже
   раскрыть аргументы, детали, примеры и оговорки автора. Лимит 16000 символов —
 ПРЕДЕЛ для самых объёмных и информационно насыщенных транскриптов, а не цель:
 объём sum-файла определяется объёмом и насыщенностью полного транскрипта;
 короткое или простое видео — короткий sum-файл, растягивать содержание ради
 лимита запрещено. Длина файла проверяется инструментально (`len()`) ДО записи,
 как в ПРАВИЛЕ №1; >16000 — сокращать формулировки, состав тезисов сохранить.
 Новый sum-файл попадёт в векторную базу скилла `brain-vector` ближайшим кроном
 (каждые 4 ч); если по нему нужно отвечать сразу — прогнать синк вручную:
 `~/.local/share/uv/tools/mlx-embeddings/bin/python
 ~/.hermes/skills/brain-vector/scripts/brain_index.py`.

6. **Ответ пользователю** (на языке запроса юзера):
   - **Первая строка ответа** — одной строкой: название видео, автор/канал,
     длительность, язык. Ссылка в начале ответа ЗАПРЕЩЕНА: Telegram строит по
     первой ссылке сообщения embed-превью сайта, которое раздувает сообщение;
     ссылка присутствует ровно один раз — в блоке метаданных в конце.

   **Цель резюме**: передать основные идеи, существенные факты, аргументы и выводы
   автора без искажения смысла.

   **Структура (строго, заголовки как указано):**
   ```
   # Главная мысль
   1–2 предложения.

   # Ключевые тезисы
   Маркированные пункты. Один пункт — одна законченная мысль.
   Между ЛЮБЫМИ двумя соседними пунктами — ровно одна ПУСТАЯ СТРОКА
   (см. ПРАВИЛО №2: проверяется инструментально перед отправкой).
   Количество пунктов определяется содержимым материала: столько, сколько
   нужно, чтобы покрыть все существенные идеи и выводы без второстепенных
   деталей; жёсткого ограничения нет. Общий объём всего ответа — строго ≤3800
   символов, из них на резюме (без блока метаданных) — не более
   (3800 − длина блока метаданных − 50 запаса): блок собирается и замеряется
   `len()` ДО написания резюме — метаданные и папка Brain известны заранее
   (шаги 2, 5b). Замер «в уме» запрещён (ПРАВИЛО №1). Справочно: по имеющимся
   транскриптам блок занимает 225–466 символов, в среднем ~340.

   # Вывод
   1–3 предложения: основной итог или практическое значение текста.
   ```
   Объём всего ответа (шапка + резюме + пометки + блок метаданных) —
   строго не более 3800 символов; лимит резюме вычисляется как
   3800 − len(блок метаданных) − 50 (блок замеряется инструментально заранее).
   Это жёсткое требование, а не ориентир: лимит соблюдается в каждом
   ответе, исключений нет.

   Перед отправкой необходимо убедиться, что правило не нарушено: посчитать длину
   готового текста (число символов, включая пробелы и разметку) реальным вызовом
   инструмента (`execute_code`/`terminal`, `len()`) и сверить с 3800; подсчёт в
   уме запрещён (см. ПРАВИЛО №1 в начале скилла). Если длина больше 3800,
   отправлять ответ нельзя — его требуется переписать компактнее и проверить
   снова.

   Лимит достигается только за счёт формулировок. Ни один тезис, факт, число, имя
   или пометка не снимаются ради сокращения: сжимается изложение каждого пункта,
   а состав пунктов сохраняется полностью. Ответ, из которого ради лимита убран
   материал, нарушает это правило так же, как ответ длиннее 3800 символов.

   **Блок метаданных — последний раздел ответа** (после резюме, ответов на доп.
   вопросы и пометок; отдельным сообщением Telegram его отправить невозможно —
   из одного ответа агента уходит одно сообщение). Формат — помеченные строки
   без буллетов (буллеты зарезервированы за «Ключевыми тезисами», ПРАВИЛО №2):
   ```
   # Метаданные и размещение
   Название: <title>
   Автор: <uploader>
   Дата публикации: <YYYY-MM-DD или «неизвестна»>
   Ссылка: `<webpage_url>`
   Папка Brain: <Education|Family|Finances|Health|Hobbies|Private|Work>
   ```
   Ссылка — строго в `code`-формате (некликабельная, копируется тапом): любая
   кликабельная ссылка в сообщении даёт embed-превью сайта. Папка Brain — только
   название папки, без имён файлов. Остальные значения — те же, что в шапке MD
   транскрипта. Если `~/gdrive/Brain/` была недоступна (шаг 5b), строка
   «Папка Brain» заменяется на: «Brain недоступна — файлы остались в
   ~/result-mlx-whisper/».

   **Язык:**
   - Грамотный литературный русский, нейтральный информационно-деловой стиль.
   - Не переводить с английского слово в слово — это касается не только идиом
     и терминов, но и любых слов без прямого русского эквивалента (subtle,
     thorough, nuanced и т. п.). Устоявшиеся эквиваленты — использовать
     (stepping stone → «промежуточный этап», а не «ступенчатый камень»).
     Запрещено подбирать русское слово «по оттенку смысла» и вставлять его в
     сочетание, где оно не употребляется: «subtle design taste» → «тоньше
     в дизайне» — ошибка. Если устоявшегося эквивалента нет, не сжимать нюанс
     в одно слово, а раскрыть его фразой о том, что конкретно происходит:
     «subtle design taste» → «точнее работает с мелкими деталями, анимациями
     и компоновкой»; «more thorough» → «тщательнее проверяет код». Критерий:
     русская фраза называет наблюдаемое действие или свойство, а не оттенок.
   - Без разговорной лексики, сленга, жаргона, эмоциональных оценок, риторических
     вопросов и фамильярных обращений.
   - Писать так, как пишет человек-редактор в хорошей профессиональной и
     художественной литературе: глагол вместо отглагольного существительного,
     простая синтаксическая конструкция, только те сочетания слов, которые
     реально встречаются в печатных текстах. Критерий для каждого предложения:
     могло бы оно стоять в книге или статье, написанной человеком, или это
     калька, которую породила модель.
   - Каждое словосочетание должно быть общепринятым в русском языке. Проверять
     управление ключевых слов: существительное требует свойственных ему
     предлога и падежа («по цене $500», «курс 90 рублей за доллар» — но не
     «при курсе $500»). Если конструкция не встречается в живых текстах,
     переписать её простой формулировкой, близкой к словам источника, вместо
     того чтобы изобретать новое сочетание.
   - Предложения логичные, законченные, грамматически корректные; предпочтительны
     короткие и средние; длинные сложные разбивать, если это улучшает читаемость.

   **Содержание:**
   - Сохранять ключевые факты, даты, цифры, имена, причинно-следственные связи и
     оговорки автора.
   - Не добавлять собственных интерпретаций, предположений и сведений, которых нет
     в источнике.
   - Исключать повторы, второстепенные детали и иллюстративные примеры, если они не
     важны для понимания вывода.
   - Противоречия и неопределённости в тексте — кратко отражать, а не устранять
     от себя.
   - Таймкоды в резюме запрещены — они нужны только внутри для навигации по
     транскрипту.

   **Внутренняя проверка перед отправкой:** (1) нет фактических искажений; (2) все
   предложения грамматически корректны; (3) нет разговорной лексики, повторов и
   «воды»; (4) структура соблюдена, включая пустую строку между каждыми
   соседними пунктами «Ключевых тезисов» (ПРАВИЛО №2); (5) резюме понятно
   без обращения к исходнику;
   (6) длина посчитана и строго ≤3800 символов, при этом состав пунктов сохранён:
   сокращение шло за счёт формулировок, а не за счёт снятия тезисов.

   - **Ответы на дополнительные вопросы из запроса** — отдельным блоком ПОСЛЕ
     резюме (структуру резюме они не нарушают), цитируя конкретные места
     транскрипта (по таймстампу — тут таймкоды уместны), а не пересказ.
   - Пометка о ненадёжном распознавании — только когда «каша», сомнительные имена
     или термины реально касаются фактов, цифр или имён, вошедших в резюме: тогда
     после резюме отдельной строкой указать, какие именно пункты это затрагивает.
     Если ненадёжные фрагменты — только обрывки реакций поверх шума, а все факты,
     числа и имена резюме подтверждены субтитрами или списком терминов, пометку
     не добавлять вовсе: она превращается в формальный шум.

     ## Procedure: не-медиа ветка («добавь в мозг» для статей, книг, файлов, текста, тем)

     A. **Получить контент**:
     - ссылка на статью/страницу/пост — tavily extract (basic; если пусто или защита —
     advanced, затем blocked-page-recovery);
     - тема без ссылки («добавь в мозг про X») — tavily search, выбрать лучший
     первичный источник, затем extract его;
     - файл-документ — прочитать (`read_file` сам извлекает docx/pdf/pptx и т.п.);
     .html — конвертер `scripts/html2md.py` этого скилла:
     `python3 ~/.hermes/skills/brain-summary/scripts/html2md.py <файл.html>`;
     - готовый текст/пересланное сообщение — как есть.

     B. **Метаданные** — тот же гейт, что в шаге 4 медиа-ветки: название (заголовок
     страницы/документа), автор, дата публикации, ссылка. Часть не определяется —
     обязательно запросить у пользователя с дефолтами: название — заголовок или имя
     файла с расширением; автор — unknown (если источник — запись или конспект Plaud, маркеры «note 1/1», «auto_sum_note», «consumer_note», «Meeting Minutes», — то «plaud»); дата — предложить текущую; ссылка —
     переданная или найденная, для файла — полный относительный путь к файлу.
     Пустые значения и молчаливый пропуск запрещены.

     C. **MD-файл**: первым — блок контент-метаданных (`- **Название:**`,
     `- **Автор:**`, `- **Дата публикации:**`, `- **Ссылка:**`), пустая строка, далее
     контент ЦЕЛИКОМ в markdown (заголовки, таблицы, списки сохранить/преобразовать).
     Это трансформация формата, а НЕ пересказ: содержание не сжимать. Имя файла:
     `YYYY-MM-DD_<короткое название>.md`. Sub-файл пересказа (шаг 5c) для не-медиа
     НЕ создаётся — MD уже содержит полный контент.

     D. **В Brain + ответ**: как шаги 5b/6 медиа-ветки — прочитать
     `~/gdrive/Brain/AGENTS.md` ПОЛНОСТЬЮ, выбрать папку по его правилам (границы в
     разделах «Чего здесь быть не должно»), записать файл, убедиться чтением копии.
     Ответ — короткий: что добавлено + блок «# Метаданные и размещение» в формате
     шага 6 (ссылка строго в `code`-формате, папка — только имя). Лимит 3800 и
     инструментальные замеры (ПРАВИЛО №1) действуют и здесь.

     ## Pitfalls

- **Язык — гейт**: язык брать только из называемого источника — заголовок/описание
  (`yt-dlp --print` до скачивания) либо детект на первых 30 с. Запуск по привычке
  или дефолту («обычно всё русское») даёт транскрипт-кашу и полный перезапуск.
- **Триггер сужен намеренно**: ссылка не на YouTube без команды скилл НЕ запускает —
  не-медиа контент идёт только по явному «добавь в мозг/brain» (шаги A–D). Не
  «улучшать» это обратно: авто-срабатывание на любую ссылку давало ложные запуски.
- Метаданные считать до скачивания: они же дают title для `--terms`.
- **Формат резюме**: строгая структура «# Главная мысль / # Ключевые
  тезисы / # Вывод» (см. шаг 6), нейтральный информационно-деловой стиль, без
  разговорной лексики и «воды» — разговорный «пересказ другу» не соответствует
  формату. Таймкоды в резюме запрещены — остаются только в ответах на доп.
  вопросы (цитаты из транскрипта).
- **Лимит 3800 — через инструментальный замер (ПРАВИЛО №1)**: «на глаз» лимит не
  соблюдается — ответ без замера уходит перебором. Счёт в уме не считается:
  только `len()` в `execute_code`/`terminal` до отправки. 3800, а не 4096,
  потому что MarkdownV2-экранирование точек/дефисов/скобок разрастает текст на
  100–150+ символов, и ответ под 4000 мост разбивает на 2 сообщения.
- **Пустая строка между пунктами (ПРАВИЛО №2)**: требование проверять так же
  программно, как и лимит — проверка «на глаз» пропускает буллеты «вплотную».
- Оба артефакта (mp3 + MD) остаются в `~/result-yt-dlp/` и `~/result-mlx-whisper/`,
  копии MD и sum-файла — в `~/gdrive/Brain/<предметная папка>/` (шаги 5b/5c) —
  когда юзер потом задаёт доп. вопросы по видео, отвечать по сохранённому
  транскрипту без повторной транскрипции.
- **Доп. вопросы после пересказа — только по готовому транскрипту**: полный MD
  уже содержит всё содержание видео, поэтому для ответов
  на последующие вопросы НЕ ходить в интернет (tavily/web_search) и НЕ вызывать
  снова yt-dlp (метаданные, описание, субтитры) — сначала перечитать
  `~/result-mlx-whisper/YYYY-MM-DD_<имя>.md` (путь виден в заголовке MD, источник
  mp3 — в метаданных) и цитировать ответ с таймстампами оттуда. Внешние
  инструменты — только если в транскрипте реально нет нужных данных (например,
  юзер спрашивает про то, чего в речи не было: описание под роликом, ссылки,
  комментарии).
